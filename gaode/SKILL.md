# 周边去哪儿

## 用途与适用场景

当用户询问起点附近的咖啡馆、餐厅、公园或其他地点，并希望知道步行距离或时间时使用本 Skill。输入通常包含城市、起点名称、起点经纬度和自然语言偏好。评测环境会提供起点坐标；直接使用给定坐标，不要用 IP 定位或自行猜测位置。

## 执行流程

1. 从需求中提取地点类别或关键词、步行时间上限、最多推荐数量、排序偏好及其他明确筛选条件。默认最多推荐 3 个；用户明确要求更少时遵从用户数量。不要把未提及的偏好当作筛选条件。
2. 使用高德 `maps_around_search`，以起点坐标为中心、以城市和需求类别构造搜索词查找周边 POI。经纬度按高德工具要求使用 `longitude,latitude` 顺序，原样保留输入和 POI 返回的坐标，不要交换或自行转换。按工具实际参数定义填写关键词、中心坐标及可选搜索半径；若结果太少，可调整关键词或扩大搜索范围后再查一次。
3. 按 POI 名称、类型和地址剔除明显不符合需求或重复的结果。优先使用搜索结果中返回的 POI ID、名称、地址和坐标。如果缺少规划路线所需的坐标，且有 POI ID，则调用 `maps_search_detail` 补查；仍没有坐标或身份信息不足以确认地点时，不要为其编造路线或推荐。
4. 对每个可确认的候选地点，使用 `maps_direction_walking` 查询从给定起点坐标到该 POI 坐标的步行路线。每个地点都是从同一起点出发的独立备选，不要把候选点串成多站行程。必须使用步行规划返回的路线距离和耗时；不要用直线距离、距离换算速度或其他模式的路线替代。
5. 根据路线结果逐个筛选。若用户给出步行时间上限，只保留工具返回耗时不超过上限的路线；比较时使用未取整的原始耗时，展示时再转换成易读的分钟。若未返回可用路线或耗时，则该地点不能算作满足时间条件的推荐。不得将超时地点混入符合条件的推荐。
6. 按用户偏好排序。“优先近一点”按步行路线距离从短到长排序；距离相同或没有明确距离偏好时，可用路线耗时作为次要排序依据。其他偏好只在搜索结果或工具数据能够支持时用于排序。最多返回用户要求的数量，且不超过 3 个。
7. 每条推荐的名称、地址、距离、耗时和理由都必须能由高德返回数据支持。理由说明地点类型为何符合需求，或路线数据为何符合用户的距离/时间偏好；不要臆测环境、口碑、安静程度、排队、营业状态或服务质量。数据没有提供或无法确认的属性明确标注“未核实”，不要将其写成事实。

## 回答格式

用简短列表或表格回答。每个地点包含：

- **名称**及**地址**（使用高德返回内容）
- **步行距离**与**预计步行时间**（使用该地点步行路线的返回值）
- **推荐理由**（仅写有数据依据的匹配点）

简要说明地点从用户起点独立出发。只有查询结果支持时才说明结果数量、排序依据或具体筛选情况。

## 结果不足与异常

- 符合条件的地点少于用户要求数量时，只列出实际符合条件的地点，并说明本次查询范围或路线结果中符合条件的地点不足；不要用不符合时间上限的结果凑数。可建议用户放宽时间、类别或范围。
- 搜索成功但没有合适地点时，如实说明没有找到符合条件的结果。不要虚构 POI、地址、坐标或路线。
- 某候选地点缺少坐标、详情或有效步行路线时，跳过该地点；若因此影响结果数量，简要说明哪些信息未能核实。
- 工具调用失败时，不要把失败说成“没有结果”，也不要编造成功数据。说明失败的是周边搜索、地点详情还是步行路线；若仍有已经成功验证且符合条件的结果，可只推荐这些结果，并说明查询受限。若无法验证任何结果，明确告知暂时无法完成查询，并请用户稍后重试或放宽条件。
